# Valenbot v2.2.0 · SN 工业工作台

根据《SN码管理系统需求确认.md》实现的独立新版，沿用初版的 Java Spring Boot、PostgreSQL、Thymeleaf 和工业工作台风格。原 v1.0.1 的源码、运行 JAR、数据库和发布包均保留。

v2.2 完成业务分层、创建与日期校验、授权查询和完整自动验收。详见 [架构与升级说明](v2.2-架构与升级说明.md) 和 [本版测试报告](变更与测试报告-v2.2.0.md)。

## 试用账号

实际密码只保存在本机 `../runtime/v2/试用账号与访问说明.md`，不打进软件包。

| 账号 | 角色 | 能力 |
|---|---|---|
| `admin_trial` | 管理员 | 新建主档、号段、业务表和字段；用户授权；配置；全部业务查询与管理 |
| `tech_trial` | 技术人员 | 维护业务字段、装拆、流程、维修、人工回读校验；已额外授权 SN 生成、作废、迁移和维修替换；可新增机器人主档和补充业务记录；不能创建号段、删除记录或修改表结构 |
| `user_trial` | 普通用户 | 仅自己绑定机器人中管理员设为客户可见的字段、二维码和常规导出；只能修改昵称 |

升级不会猜测客户归属，首次初始化的普通试用账号默认未绑定；已有账号保留原绑定，看不到任何机器人。管理员进入“用户与权限 → 管理账号与绑定”，选择一台机器人并填写客户名称和原因。权限使用稳定用户 UUID 与机器人 UUID；客户名称只用于台账展示。同一机器人只允许一个普通账号占用。技术人员可选 SN 范围，留空不限。重绑定后后续请求立即按新范围执行；重置密码、停用或修改角色会使相关会话失效。可使用右上角“修改密码”修改本人密码。

## 数据导入结果与语义

原始来源：`LB_人形陪伴机器人SN码管控表.xlsx`。读取三个工作表，保存全部非空单元格、坐标、文件 SHA-256 和字段映射。

- **10 个机器人主档**：`LBR-2609-P-0001` 至 `LBR-2609-P-0010`。
- **2 台完整度较高的机器人、8 条仅 SN 的主档**。空白不补造设备版本、客户、生产日期或安装版本。
- **26 个当前硬件模组关联**，来自两台机器人各 13 个模组 SN；版本留空。
- 46 个原表列逐列映射。**M 列是交付日期，不是激活日期**。第一台原始状态为“已交付”，昵称“小乖”；第二台“在库”，昵称“小陪”。
- 原表“测试通过”保存为整机调试结果；未填写的独立质检结果保持为空，不能推断成质检通过。
- 初始已交付状态忠实保留。后续出库或交付需通过“登记流程 → 质检”填写明确的“通过”。
- 各模组 `installed_at` 是系统登记时间；历史实际安装日期原表未给出。装配、烧录、调试、质检、交付等已提供日期独立保存为流程业务日期。
- 十个 SN 均已占用；下一次生成 `2609/P` 会从 **0011** 继续。作废和退役 SN 不再使用。
- 原表说明部分存在 `R-` 前缀、四角色、维修后缀等与确认文档不一致的叙述：仅作为来源留存，实际执行 **LBR、三角色、结构化迁移**。
- 目前模组数量上限按本次台账的 13 个类型各 1 件设置；可按实际装配要求由管理员调整。不建立 BOM 版本追踪。

“导入来源”页面可查看所有工作表、导入决策并导出来源快照。导入是初始化时的一次性过程；重启不覆盖后续人工编辑。不向公开包中放入原始 Excel 或业务数据。

## 日常使用

1. **查询与编辑**：登录后搜索 SN、昵称或型号，点击“查看档案”。按绿、黄、蓝分组编辑；硬件在装拆区管理。普通账号只看到已明确公开且未归档的字段；昵称列可见时提供“修改昵称”。修改需说明原因，多人同时编辑发生冲突时会提示刷新。
2. **新增主档**：管理员或技术人员点击“新增机器人”，填写生产年月、类型和产品信息，有 SN 专项权限时可自动生成 SN；也可输入编码中心中已预留且未使用的 SN。新建默认在库，质检、调试及交付相关字段须通过流程登记。
3. **SN 编码中心**：管理员分配号段和负责人；管理员或有专项授权的技术人员生成编号、作废未使用编号。使用 `LBR-YYMM-TYPE-SEQ`，S/P/M/R 四种类型，同月同类型递增，最高 9999。并发分配通过数据库事务和计数器锁保证唯一。
4. **流程登记**：装配、调试、质检、入库、出库、交付、现场安装、售后、维修和报废。业务日期须明确填写（补录须填实际日期）；系统保存实际操作账号、提交时间、业务日期、执行人员、结果、单据及当时的版本与装配快照。状态变化另外留痕；已报废设备不可直接恢复。
5. **硬件装拆**：安装、更换或拆卸。模组 SN 不可同时装在两台机器人，数量不得超过配置值。更换保留前后 SN、版本、操作者、原因和时间。
6. **提交维修**：填写故障说明后点击提交，自动生成日期、提交人、版本和装配快照，并转为维修中。处理时追加结果；全部工单完成后恢复在库。历史处理记录和维修前快照不能覆盖。
7. **SN 迁移 / 维修替换**：先生成未使用的新 SN，再在档案中填写新 SN、原因和审批凭证。维修替换须使用 R 类型。旧 SN 退役，旧二维码仍会打开迁移后的主档，所有历史保留。
8. **设备写入校验**：创建写入任务，使用设备工具自行写入，然后填写真实回读值及日志凭证。系统记录一致或不一致的每次结果；SN 迁移后原任务标为失效。
9. **业务表和字段**：管理员在“机器人信息管理 → 列管理 / 字段管理”新增、配置、归档及恢复主台账列。配置包括类型、顺序、必填和客户可见，新增默认仅内部可见；列表、详情、编辑表单和常规 CSV 同步变化。归档只隐藏展示，原值、SN 身份、客户绑定、昵称权限和审计继续保留。字段类型创建后固定，历史空值不补造。补充业务表则在“业务表”独立管理，管理员管理结构，管理员与技术人员新增、编辑记录，只有管理员可删除。业务表是元数据驱动的逻辑表，字段和值保存在 PostgreSQL，删除采取软删除，历史保留。
10. **导出与审计**：主档导出 CSV；完整履历、业务表、来源、用户、号段和日志导出 JSON。所有结果在服务端按角色与数据范围过滤。技术人员审计可看本人和有权机器人的记录；页面及审计导出目前最多显示最近 2000 条事件。用户和登录日志仅管理员可见。

## 一键 SN 二维码标签

台账点击“二维码”，或档案点击“生成 SN 二维码”：

- 白色横向标签，左侧三行：**Valenbot 人形陪伴机器人 / 产品型号 / SN**，右侧黑白二维码，布局参照提供的图片。
- 下载 PNG（1800×540），或下载纯二维码、打开标签打印。建议 100×30 mm，不拉伸、不裁剪二维码白边。
- 二维码内容是包含完整 SN 的地址，如 `http://192.168.110.8:8082/r/LBR-2609-P-0001`。扫码登录后按角色显示，二维码不携带软件版本或客户等隐私字段。
- 二维码地址来自 `VALENBOT_PUBLIC_URL` / 本机 `runtime/v2/config.json` 的 `publicUrl`，不使用访问者请求头拼接，避免把 localhost 或错误主机印到标签上。
- 更换服务器 IP 后需更新配置并重启、重打旧地址的标签。正式长期使用建议固定 IP 或局域网 DNS。

**当前 Flash 边界**：按用户确认，提供任务和人工回读比对页面。尚无设备协议，因此不会自动操作设备存储，也不会将人工输入标记为硬件实测成功。后续可接设备工具签名日志/串口/HTTP 接口。

## 本机启动与停止

根目录双击 **`启动Valenbot新版.bat`**，或在本工程执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-Valenbot.ps1
```

启动器读取 `../runtime/v2/config.json` 和当前 Windows 用户加密的 `credentials.xml`，不会改动旧版环境变量。8082 已占用时拒绝重复启动。终端模式请保持窗口运行，Ctrl+C 仅停止该实例；应用日志为 `runtime/v2/app.log`。PostgreSQL 仍使用现有 Windows 服务。

持续局域网运行：使用固定主机/IP，关闭睡眠；用 Windows 任务计划或服务包装器以本机相同服务账号运行启动器，设置开机启动和失败重启，日志轮转与备份保留计划。加密凭据绑定 Windows 用户，换服务账号须重新生成其凭据。此版本默认没有新增开机启动任务。

## 在其他 Windows 主机部署

需要 JDK 17+ 和 PostgreSQL 16。构建源码才需要 Maven 3.9；运行 JAR 不需要 Maven、Python 或 Docker。

1. 用 PostgreSQL 管理员建立新的 `robot_v2` 登录角色和 `robot_sn_v2` 数据库，不复用旧库。
2. 把发布 JAR 放入私有运行目录。复制 `config.example.json` 为该目录的 `config.json`，修改 JDK、数据库和局域网 URL。
3. 在目标运行账号的 PowerShell 保存数据库密码：

```powershell
$dbSecret = Read-Host '新版数据库密码' -AsSecureString
@{ DbPassword = $dbSecret } | Export-Clixml .\credentials.xml
```

4. 根据 `bootstrap.example.json` 在私有运行目录创建 `bootstrap.json`，为三类账号设置不同密码。**必须替换示例占位密码**。不带 workbook 时创建空台账；首次启动建表、账号，后续启动不重复导入。
5. 执行 `Start-Valenbot.ps1 -ConfigFile '私有运行目录\config.json'`。默认建表由 Flyway 完成。

首次导入同模板 Excel 可使用 `tools/prepare_import.py workbook.xlsx accounts.json bootstrap.json`（Python + openpyxl）。导入工具仅生成私有初始化数据，不修改原表；检查其映射报告后用于新数据库启动。已经使用过的数据库不能用初始化文件覆盖，后续追加导入应另走带核对的迁移流程。

## 备份与恢复

用 `pg_dump -Fc -d robot_sn_v2 -f backup.dump` 备份到私有目录，通过临时环境变量或 PostgreSQL 密码提示提供认证，不把密码写进公开脚本。系统已为本次部署建立初始 `.dump` 备份，位于 `runtime/v2/backups`。

恢复时新建空数据库，再 `pg_restore --no-owner --role=robot_v2 -d 新数据库 backup.dump`，先核对 SN 数量和权限，再切换服务。保留应用发布 JAR、对应 schema 与备份版本。**不要往 robot_sn 恢复新版备份。** 生产数据库磁盘文件依旧在 PostgreSQL Windows 服务的数据目录中；工作区保存的是连接配置和逻辑备份。

## 构建、测试和目录

```powershell
mvn clean package
# 产物 target/robot-sn-system-2.2.0.jar
```

`src/main/resources/db/migration` 是可复建数据库结构；`tests/test_v21.py` 覆盖本版隔离、列配置、管理员保存、会话失效和原业务回归，复用 `tests/acceptance.py` 的 HTTP 客户端。后者的原 v2.0 用例只适用于历史发布版，不能作为当前权限预期。验收服务必须连接 **robot_sn_v2_test**，端口 **8083**，设置 `VALENBOT_TEST_ACK=robot_sn_v2_test` 才允许运行。完整套件需从新的测试库开始，禁止对生产库执行。

JUnit 单元测试包括标签二维码反向解码及 CSV 公式转义。标签 UI、维修表单和多种屏宽另外通过真实浏览器验证。本版验收详情见 `变更与测试报告-v2.2.0.md`，旧 `验收报告.md` 是 v2.0 历史记录。权限与类图、时序图见 `权限与交互模型.md`。独立模块说明见工作区根目录 `SN编码中心、业务表与导入来源功能说明.md`。

分发包只包含源码、JAR、说明、示例配置和迁移 SQL；不包含 runtime、实际密码、真实数据库、原 Excel 或数据库备份。

## 从 v2.1 升级到 v2.2

本版无 schema 变更，保留 V1/V2 校验。备份后更换为 2.2.0 JAR，使用原运行配置与数据库，刷新登录页。完整测试含 34 项 JUnit 与 14 组 HTTP 验收（仅独立测试库、合成数据），准备步骤见架构与升级说明。

## 历史：从 v2.0 升级到 v2.1

先停止 v2 实例并用 pg_dump 备份 robot_sn_v2，保留原 JAR。部署 2.1.0 JAR 后，Flyway 自动执行 `V2__identity_binding_and_columns.sql`，增加稳定身份、绑定历史和主台账列配置，不重导 Excel。生产普通账号首次升级后未绑定，须由管理员明确分配。升级前后数据库结构不同，回退应将升级前备份恢复到独立库并使用配套旧 JAR；不要把旧 JAR 直接连接已升级数据库。本版启动器指向 2.2.0，不改变 v1 的启动方式。
